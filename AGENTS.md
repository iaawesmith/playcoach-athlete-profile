- Calibration library clips are reached only through the `admin-calibration-clips` function (service role); the table has no browser policies until admin auth lands (F-SEC-1).
- Library runs are tagged inside `athlete_uploads.analysis_context` (`source: "calibration_library"`, `calibration_clip_id`) rather than a new column, so the analyzer stays untouched.
- Library context mapping and override comparison live in `src/services/libraryRunContext.ts`; compare against a freshly fetched clip before submission and retain the used context on the upload for result display.
- Analyzer metric-quality rules (plausibility ranges, error-rule evaluation, window confidence gate, low-quality feedback) live in `supabase/functions/analyze-athlete-video/quality.ts` as pure code so they can be unit-tested from `src/test`.
- Analyzer calibration math (height-based per-frame scale, smoothing, spread gates, resolution parsing) lives in `supabase/functions/analyze-athlete-video/calibration.ts` as pure code so it is unit-tested from `src/test`; every run records all scale candidates in `calibration_audit`.
- Analyzer phase anchoring, catch anchoring and plant-side rules live in `supabase/functions/analyze-athlete-video/segmentation.ts` as pure code, unit-tested from `src/test`; side rules come from optional `keypoint_mapping.side_rule`, with a name/phase heuristic only as fallback, so node data stays authoritative.
- Pose-service framing rules (zoom gate, path-fit crop = min(cap, fit), athlete-sized recovery crops, following-crop planner, partial-detection limits) live in `mediapipe-service/app/framing.py` with no MediaPipe imports so `mediapipe-service/tests/test_framing.py` runs without the model; all recovery runs on original frames through a separate IMAGE-mode engine, never the main VIDEO tracker.
- Analyzer temporal smoothing lives in `supabase/functions/analyze-athlete-video/smoothing.ts` as pure code (unit-tested from `src/test`); missed/rejected frames are never positions and smoothing never writes a point into a frame that had none, so gaps can't produce fabricated coordinates. The smoothing window is a dedicated analyzer constant, never a metric's `temporal_window` (that is the measurement window), so smoothing can't flatten what a metric measures.
- Analysis Log reporting uses a pure frontend adapter for configured measurement windows and active-metric confidence checks; recorded service metadata is joined during result normalization, never written back or used for scoring.
- Coaching prompt formatting (metric lines with "Measures:" first sentence, run context, placeholder rendering for template and system instructions) lives in `supabase/functions/analyze-athlete-video/prompt.ts` as pure code, unit-tested from `src/test`, so the model only sees what was measured.
- Feedback replay for prompt tuning goes through `admin-replay-feedback`, which calls the analyzer's service-role-only replay mode; replays never write results.
- Coaching feedback checks and data-only fallback construction stay in the pure prompt helpers; fallback excludes node correction prose and checks every complete line so rejected wording cannot escape through fallback.
- Metric scoring and direction-aware target wording (`target_direction`) live in `supabase/functions/analyze-athlete-video/scoring.ts` as pure code shared by the analyzer, prompt helpers and frontend, so every surface describes a value the same way it was scored.
- The coaching model is resolved in one place (`supabase/functions/_shared/coachModel.ts`: replay override, then node override, then workspace `coaching_model_settings`); replays and comparisons may override it but never persist it, and prompts never carry athlete names (inserted after the feedback check).
